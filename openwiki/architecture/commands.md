# Commands, views and the write guards

Four commands, declared in [`package.json`](../../package.json), each `name` mapping to
`src/<name>.tsx`. `ray build` fails if a declared command has no entry point, which is the only
thing that catches a manifest typo.

## Search Applications

[`src/search-applications.tsx`](../../src/search-applications.tsx) is thin. It loads the
instance registry, owns the scope dropdown (persisted to `LocalStorage`, so an operator who
works in one instance stays there), and hands everything to
[`ApplicationListView`](../../src/ui/ApplicationListView.tsx).

That component is shared with the ApplicationSet drill-down, which is why it takes an optional
`filter` predicate and an `emptyTitle` rather than knowing about either caller. Its rendering
rules are in [the read path](read-path.md#4-the-list-never-renders-more-than-a-capped-number-of-rows).

Rows come from [`ApplicationListItem`](../../src/ui/ApplicationListItem.tsx): name, project,
sync and health icons, a layers icon when the application was generated by an ApplicationSet,
and the instance name as a coloured tag when more than one instance is in scope.

## The application detail view

[`src/ui/ApplicationDetail.tsx`](../../src/ui/ApplicationDetail.tsx).

The ordering of this view is its whole design. An out-of-sync application raises exactly one
question, "out of sync in what way", so the resources that answer it come first and the
metadata comes after:

1. The operation message and any `status.conditions`, as block quotes.
2. **The resources needing attention**, one per line. This costs no request:
   `status.resources` arrives inside the application object.
3. The commit actually deployed, with author and message. One small request to
   `revisions/{revision}/metadata`, swallowed on failure since it is context.
4. Recent deployments, with who triggered each (`initiatedBy`, or `automated`).
5. Images, then the last sync **failures** only.

Two lessons are baked in here. **No markdown tables**: the detail pane is a few hundred pixels
wide and Raycast wraps a table cell by breaking the word, so a `Status` header rendered one
letter per line. And the sync-message section lists only `SyncFailed` resources and failed
hooks, because listing every resource carrying a message means listing every resource on a
successful sync, each saying `serverside-applied`, which buried the ones that mattered.

The metadata panel carries the **sync policy** as tags (`automated`, `prune`, `self-heal`, or
`manual`) next to the sync status rather than buried, because whether auto-sync is on changes
what a manual sync means.

A failed load is rendered, not thrown. The view keeps the cached row it was opened from,
prefixes the markdown with what went wrong, and offers the recovery that matches the instance's
auth mode. Before that, an expired session here produced a stack trace while every list view
reported the same failure properly.

Two views push off it:

- [`ResourcesList`](../../src/ui/ResourcesList.tsx): the full inventory, attention first, with
  per-resource sync and health, sync wave, `prune` and `hook` tags. No request. Each resource
  offers its own diff, a deep link, and a **Copy kubectl command** action.
- [`ResourceDiffView`](../../src/ui/ResourceDiffView.tsx): the diff, computed locally. See
  [the ArgoCD API page](../domain/argocd-api.md#the-diff-field-is-declared-and-empty).

## Search ApplicationSets

[`src/search-applicationsets.tsx`](../../src/search-applicationsets.tsx) with
[`useAppSets`](../../src/ui/useAppSets.ts). It merges two sources because neither is sufficient
alone, which is explained in
[ApplicationSets](../domain/argocd-api.md#applicationsets-are-filtered-silently).

Each row carries a rollup computed locally from the applications cache: total, out of sync,
degraded. Selecting one pushes
[`AppSetApplications`](../../src/ui/AppSetApplications.tsx), a pure client-side filter over the
same cache, so it opens instantly and never costs a second round trip.

## Monitor

[`src/monitor.tsx`](../../src/monitor.tsx), `mode: menu-bar`, `interval: 10m`.

It does two jobs. It reports, and it refreshes the on-disk cache, which is what keeps Search
Applications painting instantly the rest of the time. The design spec originally listed this as
a non-goal because polling every instance multiplies the cost of the scale constraint;
streaming removed that objection, and the cache-warming was a second reason the original note
missed.

The aggregation is pure and tested in
[`src/lib/monitor/summary.ts`](../../src/lib/monitor/summary.ts) because its decisions are
editorial, not technical. See [layering](layering.md#what-each-layer-holds).

A background command **cannot ask for a login**, so an instance that fails is reported with its
reason and a menu item that opens where it gets fixed, routed on `problemKind` (`unreachable`,
`auth`, `other`) derived from the error class. The last numbers it had stay on screen rather
than the menu emptying.

The icon uses the extension's own mark when healthy rather than a faint grey circle, and carries
a title while loading. That is not decoration: a grey circle with no title is indistinguishable
from nothing in a menu bar holding a dozen items, and an item that cannot be found is not a
quieter report, it is an absent one.

## Manage Instances

[`src/manage-instances.tsx`](../../src/manage-instances.tsx) and
[`InstanceForm`](../../src/ui/InstanceForm.tsx). Instance shape and validation are in
[`src/lib/config/instances.ts`](../../src/lib/config/instances.ts).

Each row shows the reachability dot with the server version and round-trip time, the write
state, the environment, and for single sign-on instances whether a renewable session exists, so
that state is visible before it fails.

## The write guards

Production is read-only, and that is enforced three times over.

1. **A `prod` instance is created with `allowWrite: false` and cannot be created otherwise.**
   `validateInstance` forces it, and `parseInstances` forces it **again on read**, so
   hand-editing `LocalStorage` cannot turn a production instance into a writable one.
2. **With writes off, the sync actions do not exist in the UI.** `ApplicationDetail` renders
   that whole `ActionPanel.Section` conditionally.
3. **The client refuses independently.** `ArgoClient.sync` throws `ReadOnlyInstanceError`
   _before it builds a request_, and a test asserts `fetch` is never called. The duplication is
   the point: a UI regression must not be able to produce a write against production.

Server-side RBAC remains the real control. These guards keep an accidental keystroke from
reaching it.

Beyond that, [`SyncForm`](../../src/ui/SyncForm.tsx) puts **Dry run** first, and everything but
a dry run goes through a `confirmAlert` naming the application, the instance and its
environment. The request body is assembled by the pure
[`buildSyncRequest`](../../src/lib/argocd/sync.ts), which returns `{}` exactly for an untouched
form, meaning "sync with the application's own settings". A `Form.Description` shows
`describeSyncRequest` of the current values, so the operator reads what is about to be sent.

## Adding a command

1. Add it to `commands` in `package.json` and create `src/<name>.tsx` with a default export.
2. Get instances from [`src/ui/storage.ts`](../../src/ui/storage.ts), never from a preference.
3. If it reads applications, use
   [`loadApplications`](../../src/ui/loadApplications.ts) rather than the client directly. It
   carries the ordering and the memory reasoning.
4. Run `npx ray build`. A declared command with no entry point fails there and nowhere else.

## What to watch out for

- **Raycast's ESLint config rewrites shortcuts** to `Keyboard.Shortcut.Common.*` when they
  match a common binding, and enforces title case on action titles. Run `npx ray lint --fix`
  and read what it changed rather than fighting it.
- **`filtering={false}` is deliberate** on both list commands. Turning Raycast's filtering back
  on would render every row.
- **An action offered must match the instance's auth mode.** An earlier version offered an SSO
  login on a token instance, where it cannot help.
